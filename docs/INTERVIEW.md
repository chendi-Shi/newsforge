## 1. 你怎么证明没有时间泄漏？

**回答：** 我先在官方 train 内按时间切出较早约 85% 的训练期，cutoff 同秒曝光整组保留；较晚部分只作内部验证，官方 dev 留到最终。词表、IDF、SVD、类别词表只从训练期已出现的新闻拟合，训练负例池只从 split 0 的同曝光未点击候选产生。验证与 dev 新闻只能经过冻结的内容转换器，用户历史直接用请求自身提供的过去历史，不由当前候选标签重建。新闻 ID 只是数组地址，没有可学习 ID embedding。

**追问：dev 文件都读进来了，还能叫留出吗？** 预处理会解析它的标签以建立数组和质量统计，但不能用这些标签拟合、挖掘负例或选模型。“留出”是实验用途约束；我不会声称其文件从未被读取。通过 split 检查、负例缓存边界、训练/验证 row IDs、manifest/hash 和训练轨迹验证此约束。

**进一步实验：** 用完全虚构的小数据，在内部验证或 dev 文本加入独有词、在标签里做扰动，验证训练词表/训练样本构造不变；核对时间 ties、未知类别和 train/dev 同 ID 元数据冲突策略。新闻 first-seen 是首次日志可见时间，不是发布时间，若获得可靠发布时间应重新比较时间过滤规则。

## 2. label=0 就是真负例吗？这份数据存在什么偏差？

**回答：** 它表示新闻在这次已记录曝光里未被点击，提供比“任意全库新闻”更明确的曝光条件，但不等于用户永远不喜欢它。日志来自已有推荐策略，曝光、位置、新闻时效和用户活跃度都会影响观察到的反馈，因此离线比较衡量的是这份曝光分布上的预测效果，不自动等于换策略后的线上收益。未曝光新闻没有负反馈标签，不能直接当成全库真负例。

训练使用 1 正 + 4 负，目标是区分同曝光候选。这样改变了先验；尤其 model-dependent hard mining 会改变负例条件分布，输出 sigmoid/softmax 或 GBDT 概率不能直接解释为总体 CTR。数据没有提供可靠的曝光 propensity，本轮不能把普通重加权称为已完成 IPS 反事实校正。

**进一步实验：** 在内部验证分析曝光候选数、时间、历史长度和重复点击分组；若能获得随机曝光或可靠 propensity，再设计离线策略评估。校准实验应在预先划定的未重采样校准集上进行，与最终 dev 分开，并报告校准条件和适用分布。

## 3. 你的 hard negative 到底怎么选？为什么先 warm-up？

**回答：** 每个训练曝光先用固定 seed 生成 16 个同组未点击新闻的池，排除这个曝光所有点击新闻 ID。`mean_random` 每次从池里取 4 个随机负例；`mean_mixed` 第 1 轮也随机，第 2 轮用当前模型无梯度地给这 16 个负例打分，选最高的 2 个，再混入 2 个随机负例。短池和 hard/random 重叠允许重复，明示为重复样本，不偷偷用 PAD 补齐。

warm-up 的动机是避免刚初始化的分数就支配难例选择；它不保证改善，仍需对照。两个均值双塔的结构、参数量、训练正例预算、seed、优化器和梯度步数一致。混合采样额外做了候选打分，所以训练时长不相同，要报告实际成本。

**追问：最高分负例可能是假负例，为什么还挖？** 正是风险所在：模型很喜欢但用户当时没点，可能只是未注意或反馈延迟。混合随机负例是有限的缓解，不是证明消除了假负例。第 2 轮选出的模型也可能不如第 1 轮，协议允许内部验证选择 warm-up checkpoint，并如实报告。

**本轮结果：** 混合双塔最终 nDCG@10 为 `0.3833533 ± 0.0095473`，随机对照为 `0.3858138 ± 0.0071019`，这里的 ± 是三个 seed 的样本标准差。混合方案相对随机低 `0.246054` 个百分点，用户聚类 95% 区间为 `[−0.272370, −0.218324]`。我保留这个负结果；但 seeds 17、43 选择的是第 1 轮，只有 seed 29 选择第 2 轮，所以 2/3 最终混合权重没有难例更新。这说明本轮“内部选 epoch 的混合训练方案”未获益，不能直接断言难例更新本身造成了全部下降，更不能推广为所有 hard-negative 方法无效。

**进一步实验：** 固定容量与预算，在内部验证比较 0/1/2/4 个 hard negatives、池大小及 warm-up 长度，记录重复率和难例分数分布；任何新选择都需要独立验证预算，不能看完最终 dev 后挑最好的配置继续宣称留出评估。

## 4. 为什么加 GBDT？神经模型赢了能说明 attention 有效吗？

**回答：** 只胜过热度或 cosine 内容匹配证据太弱。最初的 GBDT 用历史最大/均值/top3 相似度、类别重合、画像距离、历史长度等 15 个统计特征学习非线性规则。看到其内部验证结果后，我追加 rich 内容方案，让树模型也能直接利用一部分原始内容表示：保留 15 维统计，再加入候选与有效历史均值各自前 16 维 SVD、候选与历史均值各自 19 维类别向量，总计 85 维。19 维类别包含未知类别列；两套方案都不使用新闻 ID、标签特征或全训练期点击率目标编码。

两套树模型实际使用相同的 50 万正例对，各配 4 个同组负例，共 250 万二分类样本；固定 seed 2026、80 轮、学习率 0.1、31 个叶节点、L2 正则 1.0、关闭 early stopping 和 1 个 CPU 线程。固定超参数之后仍然进行了内部特征选择：在相同的 12,000 个内部验证曝光上，15 维方案的 nDCG@10 为 0.33947626，85 维 rich 为 0.37283756，因此选择 rich。原始结果和追加原因保存在 `reports/gbdt_feature_ablation.json`；这一步发生在官方 dev 解锁之前。

**追问：追加特征会不会让实验口径变了？** 会增加开发期的模型选择预算，所以必须披露是在看到 15 维内部结果后追加，并保留两套结果。它属于自适应内部验证开发，不能说全部特征实验都在观察结果前确定，也不能把用于选择的内部指标当作独立泛化证据。最终只对内部选定的方案执行锁定 dev 评估，并保留选择记录。

神经模型对全部 eligible 正例运行两轮、三个 seed。它与 GBDT 的目标、特征、样本量、容量和选择预算不同，不能叫严格消融。候选 attention ranker 相对双塔也改变容量和交互方式，赢或输都不能单独归因于 attention。若 GBDT 更强，应保留这个结果，而不是只展示较弱对照。

实际正式 dev 上，ranker 的 nDCG@10 为 `0.3858421 ± 0.0033714`，所选 GBDT rich 的单 seed 结果为 `0.3854632`；两者都接近随机双塔的点估计。不能只看 ranker 均值略高便声称 attention 带来稳定提升，也不能把 GBDT 点值接近解读成模型等价。完整结果与预算一起保留在 [实验协议](PROTOCOL.md) 及原始报告中。

**进一步实验：** 给神经方法相同的 50 万正例预算，再给 GBDT 逐步增加样本预算，画质量/时间曲线；另加容量接近、固定历史池化的 ranker，隔离候选相关聚合的贡献。这些是下一轮实验，不是已经取得的结果。

## 5. 为什么分开报告排序、点击召回和 ANN 近似率？

**回答：** 它们的候选空间和分母不同。官方排序只在每次日志的完整曝光候选里计算 AUC/MRR/nDCG，然后逐曝光等权平均。全库召回从按时间可用的新闻池检索，检查已记录点击是否进入 top-K；未曝光新闻的相关性未知。ANN 近似率只比较 HNSW top-K 与相同过滤规则下 exact top-K 的重合度，完全不需要点击标签。

MRR 还容易讲错：MIND 对这个曝光的所有点击倒数排名取均值。例如两次点击排第 1 和第 3，结果是 `(1 + 1/3)/2`，不是只取首个相关项得到 1。AUC 也不能把所有曝光拼起来算一个全局值来替代宏 AUC。

召回服务会排除已看新闻，所以同时报告全部点击分母与 eligible 点击分母，避免重复点击被服务过滤后隐形消失。重排同一 top-100 不会改变 Recall@100，应检查 top-10 等头部指标。即使 ANN 完全找回 exact 邻居，也不能证明这些邻居对用户相关。

**本轮结果：** 在 5,000 个固定 dev 请求中有 7,576 次日志点击，排除 16 次已读重复点击后 eligible 为 7,560，其中训练未见新闻的 eligible 点击为 5,686。两阶段 Recall@100 为 `0.0081837381`，也就是 62/7,576，约 **0.82%**；这个全目录点击覆盖仍低，是需要如实报告的短板。另一个内部验证样本有 128 个请求，3 个空历史未参与 ANN 非零向量比较；实际 125 个查询的 HNSW 邻居 Recall@100 为 `0.89128`。89.128% 的近似邻居重合度不是 89.128% 的点击召回，更不能证明推荐效果可上线。证据分别见 [点击召回](../reports/retrieval_experiment.json) 与 [服务基准](../reports/service_benchmark.json)。

**进一步实验：** 对相同真实查询比较 exact 与不同 `efSearch`，同时画 ANN 邻居覆盖/延迟曲线和点击 Recall 曲线；把检索丢失与重排顺序错误分开分析。所有时间过滤和 seen 过滤必须一致。

## 6. 三个 seed 和 user bootstrap 分别回答什么？

**回答：** seeds 17、29、43 控制模型初始化、训练顺序与随机负采样，三次结果的均值/样本标准差描述这三次训练的波动；三次很少，不能夸成充分估计了训练分布。模型 epoch 全部在同一固定 12,000 个内部验证曝光上按 nDCG@10 选择，不能用 dev 选择最好的 seed 只汇报它。

同一个用户会产生多个相关曝光，直接把它们当独立样本 bootstrap 会低估依赖。当前配对统计先对每个曝光的三个 seed 指标取平均，再算相对 `mean_random` 的差；以用户为簇有放回抽样 500 次，保留每次抽中用户的全部曝光，给曝光宏平均差的 95% 分位数区间。它不是分数 ensemble，不是用户等权的用户宏 AUC，也没有把有限训练 seed 不确定性完全合入置信区间。

本轮 ranker 相对随机双塔的 nDCG@10 差仅 `+0.002829` 个百分点，用户聚类区间为 `[−0.048861, +0.052756]`，跨过零，因此没有 nDCG@10 稳定提升证据。混合方案的区间虽全为负，也只是这些已训练权重在评估用户抽样下的证据，不能代替更多训练 seed 或因果归因。项目可以展示可信的失败结果和完整工程证据，不能写成 SOTA、线上 CTR 提升或腾讯业务收益。

**进一步实验：** 如果效应接近零或 seed 波动明显，增加预先固定的训练 seed，并研究同时处理训练与用户抽样的分层推断。不要只根据一次点估计或“区间没跨零”就声称线上收益。

## 7. 批量服务为什么还要锁？并发数增加就会提速吗？

**回答：** 当前是一台 CPU、一个服务 worker，`RecommendationEngine` 用锁包住推理与关闭操作，避免共享模型/内存映射资源操作冲突和请求线程池把底层算子线程过量叠加。锁意味着并发请求的核心推理串行化；不能把客户端 concurrency=4 宣称成四倍模型并行。

`/recommend_batch` 最多合并 32 个请求，对用户编码和候选评分摊薄调用成本；重排候选按有界 chunk 构造张量，避免一次分配全部候选交互。各请求有自己的时间和已看新闻过滤，ANN 搜索仍按请求处理，不能声称整条流水线都做成一次批量检索。换 checkpoint 后新闻向量与索引依赖会变化，要通过版本/hash 校验，不能混用旧向量和新用户塔。

真实 localhost HTTP 测试需要同时报告 batch、并发、线程、warm-up、错误数、p50/p95、wall time、推荐 query/s 与进程 RSS。一个 batch 请求的 RTT 不等于每个用户的延迟；ANN 局部计时不包含用户编码，而 HTTP RTT 包含服务端完整流程。当前基准在共享桌面运行，不能当生产 SLA。

**本轮实测：** 128 个内部验证请求每种配置重复 3 遍；batch=1、并发=1、单 worker 且 PyTorch/FAISS 各 1 线程时，384 个 HTTP 请求的 p95 为 `30.5672 ms`，吞吐为 `69.718 query/s`。batch=1/8 与并发=1/4 的四种组合均零错误，但 batch=8、并发=4 的 p95 达到 `140.4223 ms`，不能只报最有利的数值。后台 CPU 活动未控制，这些是一次真实本机测量，不能外推线上容量或分布式加速。

真实演示用 20 条历史构造 100 个候选，返回 10 条推荐；时间边界、模型/索引版本、过滤和标题展示等 6 项核验全部通过，见 [演示证据](../reports/demo_verification.json)。这证明流程可用，不证明推荐足够相关；结合约 0.82% 的全点击 Recall@100，不能以低延迟或漂亮演示替代质量改进和线上 A/B 证据。

**进一步实验：** 在独立机器控制背景负载，比较 batch=1/8、并发=1/4 等组合，观察锁等待、尾延迟和吞吐；再考虑有队列时限的动态 batching 或多个独立 worker，并测量模型/索引复制后的内存和一致性成本。

## 8. 你如何扩展到分布式？这能对应 JD 的并行算法要求吗？

**回答：** 已实现的证据是本机 CPU 向量化、批量模型计算、mmap 数据访问、冻结向量缓存和 ANN 服务。我能解释并行设计与扩展方案，但没有多机、多 GPU 运行证据，简历不能写“完成分布式加速 X 倍”。

下一步可以将 eligible 正例按全局索引分片，用分布式 sampler 保证每个全局 epoch 的覆盖和可复现顺序，再用 DDP 同步模型梯度。同曝光负例池与全局固定特征应只读共享或按 shard 管理；hard mining 用各步当前模型，需明确副本参数同步和缓存失效边界。索引服务可做分片召回后合并与统一重排，但必须处理 top-K、时间过滤、版本切换和跨分片重复。

**进一步实验：** 先验证单进程与多进程的数据覆盖/梯度逻辑，再测通信时间、吞吐、扩展效率、CPU/GPU 利用率、峰值内存及质量漂移。相同 epoch 数但有效 batch 改变时，学习率和更新步数也会变，不能直接把速度差当同预算算法加速。

## 9. 你怎样减少 CPU 评估的无效计算？

**回答：** 我观察到完整候选评估按原 row 顺序组成 batch 时，短曝光会补齐到本 batch 最长候选列表，产生大量 padding。于是在 dev 仍锁定的阶段，新增一个调度包装：只按候选数稳定排序曝光，再调用冻结的原评估器，最后把每曝光指标恢复到原 row 顺序。没有删掉候选或改组内排名，也没有改变训练、选模和指标定义；恢复 row 顺序是保证不同模型和用户 bootstrap 仍按同一曝光配对的必要步骤。

ranker seeds 17、29、43 的所选 epoch 1 权重均已在相同固定内部 12,000 组通过检查，共有 477,756 个真实候选；总计算槽位从 1,906,752 减为 482,624，padding 从 1,428,996 减为 4,868。三组恢复后的逐曝光 AUC/MRR/nDCG@5/nDCG@10 最大差均为 0；汇总求和顺序差约 `5.55e-17`，seed 17 出现在 MRR，seeds 29、43 出现在 nDCG@5。三份 `reports/evaluation_scheduler*validation_12000.json` 及其摘要写入神经 preflight，核验对象为指标而非 logits 的逐位一致性。

所选 85 维 GBDT 也采用这个调度原则，保留原特征、分类器与 batch size 64。在相同的 12,000 组上，逐曝光四项指标和汇总值的差均为 0；总槽位由 2,217,760 减到 486,720，真实候选数仍为 477,756。正式证据保存在 `reports/gbdt_evaluation_scheduler_validation_12000.json`，已用仓库命令 `python -m newsforge.benchmark_gbdt_scheduler --threads 1 --output <新的报告路径>` 独立复查，避免覆盖原证据。
