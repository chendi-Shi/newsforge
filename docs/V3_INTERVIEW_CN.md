# NewsForge v3：面试中的方法、证据与边界

这份说明对应仓库已经实现并完成原始数据重建的方案。本次 31 阶段全链结果见 [原始重建实测](../reports/raw_rebuild/RESULTS.md)，历史发布数值见 [MIND 原发布实测](../reports/V3_RESULTS.md)，外部结果见 [Adressa 讨论](../reports/external/adressa_v1/DISCUSSION.md)，复验范围见 [交付报告](../reports/DELIVERY_RESULTS.md)。介绍项目时先明确任务、对照和分母，再讲数字；不要把不同版本、不同数据集或不同机器负载下的结果拼成一个提升。

## 1. 这个项目究竟解决什么问题？

在严格滞后反馈、固定 100 个候选和普通 CPU 的条件下，研究个性化能否改善强热度基线的前十日志点击覆盖，同时把数据处理、训练选择、统计验证和实际服务连接起来。项目使用公开 MIND 数据，没有腾讯内部数据。

v1 训练了 PyTorch 双塔和候选相关注意力模型；v2 加入时间统计与 HGB 特征排序；v3 处理的是一个具体负结果：曝光内排序变好，目录推荐的前十覆盖却未必变好。最终方案采用轻量线性成对偏好残差，不把它称为新的深度网络。贡献在受约束的实现、对照实验、时间边界和可核验的服务交付；相关方法来源及独立实现范围见 [RELATED_WORK.md](RELATED_WORK.md)。

本次原始重建的 [v1 神经消融](../reports/raw_rebuild/V1_REBUILD.md)也保留了负结果：混合难负例的 nDCG@10 比随机负例低 0.2623 个百分点；注意力模型的 nDCG@10 差值区间跨零。九组均完成两轮训练，但五组选中第一轮，只有一组难负例配置最终保留第二轮更新。因此这里比较的是训练策略加内部验证选模，不能描述为固定两轮下难负例的纯因果效果，也不能声称每个神经组件都提升了排序质量。

## 2. 为什么 nDCG 提升，不一定让目录召回变好？

曝光内排序只重排日志已经展示的一组新闻；目录推荐先从当时可见的新闻中生成候选，再看日志点击是否进入前十。它们的候选分布和任务不同，曝光日志本身也受原系统影响。在已曝光候选上拟合的分数不能保证适用于全目录候选。

因此分别报告曝光内 nDCG 与目录 Recall，不把两者相减或将曝光内提升解释为线上 CTR。MIND v3 的主分母是固定 5,000 个请求中的 **7,576 个日志点击**，不是 5,000：原发布基线命中 1,779 个，完整方案命中 1,811 个，增量为 32 / 7,576，即 **0.4224 个百分点**。这也不是“提升了 0.4224% 的线上点击率”。

## 3. 有界残差约束了什么？

同一请求的候选首先按热度确定原排名 `r`。模型从历史与候选的 13 维内容交互中学习成对偏好，各 seed 分数先截断到 `[-1, 1]` 再平均，得到 `z`：

```text
score = -r + δ × n/(n+5) × z
```

`n` 为参与特征的有效历史长度，最多 20；调参只选择 `δ∈{0,2,5,10}`。空历史和 δ=0 严格返回热度顺序，分数并列保留原顺序。因为每项扰动绝对值不超过 δ，原排名距离大于 2δ 的两项不能逆序；边界相等时仍保留原顺序。这个性质不代表单项最多移动 δ 位，也不保证质量必然提高。

模型只改变同一批候选的顺序，因此逐请求 Recall@100 必须完全不变。若它变化，应先查实现或实验条件，而不是把变化计为重排收益。

## 4. 怎样控制时间泄漏和反复选方案？

请求时刻为 `t`，公共反馈只使用 `timestamp < floor(t/3600)*3600−3600` 的事件；等于截止点的事件也排除。文章还须满足 `first_seen < cutoff`。一小时成熟延迟是缺少实际反馈到达时间时的回放假设，首次观察也不等于真实发布时间。

2019-11-14 的拟合、调参、确认分别位于 09–13、14–18、19–23 时段，中间留成熟缓冲。拟合只估计权重和标准化；调参只选 δ；确认只执行预定门槛，不再选择消融赢家。服务使用确认门的实际决策，未通过则回退基线。

官方 dev 已被前期版本观察，不能称为全新未见测试集。分段验证约束本轮参数选择，却不能消除先前结果对方法设计的影响。MIND 离线输入历史为最近 20 条，已读过滤也仅覆盖这次传入的范围；API 则过滤传入的全部历史，并对最近 20 条提取特征。两者不能混称完整原始用户历史过滤。

## 5. 消融和置信区间怎么解释？

三个种子使用固定负例抽样，各特征变体在同一 seed 内复用配对。`no_category` 仅去掉两列显式类别重叠，完整向量相似度仍含类别分量；`no_recent` 仅去掉最后历史专用交互，最后一次行为仍参加聚合。它们是列组消融，不是把某类信息完全删除。

MIND 原发布消融没有证明这些组件各自有稳定正收益。dev 上 `no_gate` 点值更高，也不能据此替换确认前冻结的方案。先说明差值是“完整减消融”还是“消融减完整”，再解释符号。

配对用户簇 bootstrap 把同一用户的请求一起重抽，保留方法之间的一一配对；每轮计算总命中差除以总分母，而不是先算每个用户的比率再平均。区间条件于已实现的反馈与日期，不等于跨日期保证；探索性消融没有多重比较校正。协议和公式见 [V3_PROTOCOL.md](V3_PROTOCOL.md)。

## 6. Adressa 负结果说明了什么？

在另一个出版商的挪威语历史访问中，原发布的英文 MIND 表示与模型冻结不变，每日等额抽取 5,000 请求、共 15,000 请求。完整方案的 HitRate@10 为 **29.1600%**，基线为 **29.5333%**，差 **−0.3733 个百分点，95% CI [−0.5814, −0.1598]**。本次不支持直接正向迁移；门控相对无门控减轻了退化，仍没有超过基线。

文章中 24.83% 的文本表示为零；所选类别字段在映射前全部解析为空，最终 100% UNKNOWN。类别变体仍可能因不同的冻结权重、标准化和截断产生不同结果，不能因此宣称类别语义迁移成功。69.11% 的原始行未通过文章标识规则，结论只覆盖保留事件与固定样本，也不是按原始日流量加权的三日总体指标。

这些条件同时变化，本实验没有识别负迁移的唯一原因。它没有曝光负例，不能报告曝光 AUC 或校准 CTR；2017 年历史数据也不能冒充对未来的前瞻验证。首次处理还因行数上限失败，修订发生在部分事件已读取、效果未产生时；应主动交代这一执行偏差，不能说所有资源设置完全事前注册。

## 7. CPU 加速的证据是什么？

v3 热度路径缓存小时排序和成员关系，按已读集合过滤足够长度的前缀，并移除这条路径无用的双塔计算。它与旧实现输出相同的候选及字段。

本次原始重建的同请求 ABBA 测量中，v2/v3_fast 的检索墙钟耗时比为热小时缓存 **2.5456×**、冷派生缓存 **1.0699×**；1,536 个候选批次的九个字段完全一致，证据见 [本次执行摘要](../reports/raw_rebuild/execution_summary.json)。原发布对应观测为 warm **2.593×**、cold **0.977×**，历史冷态没有加速，因此不能主张稳定的冷态收益，也不能将两次观测拼成同一组对照。

该测量只覆盖检索调用，不包含 HTTP、重排或预热；cold 指派生状态冷态，不是清空操作系统缓存。本次 HTTP 的 batch=1、concurrency=1 为 **29.414 query/s、请求 p95 73.876 ms**，其他三组配置单独列在 [交付报告](../reports/DELIVERY_RESULTS.md)。共享桌面不同时刻的 HTTP 时延不能相除后称算法加速，检索比值也不是 HTTP 加速或多机分布式加速。

## 8. 怎样证明结果能交付，而不仅是表格好看？

本次已经完成本地研究与交付闭环：从四个原始 MIND TSV 重新预处理，执行 v1/v2/v3 训练、选择、评估与消融，再经过真实 localhost HTTP、独立审计和最终验收。**31 个阶段全部成功**，[整链验收](../reports/raw_rebuild/acceptance.json)与[执行摘要](../reports/raw_rebuild/execution_summary.json)均通过；45 包隔离环境来自哈希锁安装，raw 工作区是 `pipeline init` 创建的独立源代码副本，不是新 Git 克隆。数据与模型绑定、训练记录、冻结选择和保存数组核验均有对应证据。

本次 raw 工作区的全套测试为 **258 项发现、256 项通过、2 项权限跳过**，另跑 **193 项研究测试全部通过**，两者覆盖重叠。较新代码快照的 [GitHub CI](../reports/raw_rebuild/ci_checkpoint_selection.json)为 **375 项全部通过、0 项跳过**，但未执行完整数据训练或 HTTP。真实 raw 服务另完成 **768 个正式查询、13 项接口契约**，错误、失败查询和离线不匹配均为 0。

历史两份 Git 克隆与 36 包环境的复验另行保留：从冻结处理数据重训的九个 v3 线性模型字节一致、62 项对照通过，只证明那个起点下的复验。此次原始重建的 SVD 参数和文本向量并非逐位一致；v3 confirm/dev 的科学汇总字段相同，也不能扩展成模型或逐请求数组字节一致。

Adressa 的 128 请求慢速路径重新构造时间状态、历史和分数，结果一致；它共享冻结的内容特征定义，不是完全独立的模型实现。全部 15,000 请求的补充验收核对保存数组、指标和摘要链，但没有再次解析原归档或重抽 bootstrap。该外部负结果针对旧发布模型，没有验证本次 raw 新模型的外部泛化。哈希、单元测试、数值审计与效果验证各回答不同的问题。

复验入口见 [交付指南](DELIVERY.md)，完成结论来自实际阶段凭据、`raw_acceptance` 和 `raw_report`，不能以流水线计划或 CI 绿色代替。本地闭环已经完成，但 MIND dev 已经观察过，外部迁移也有负结果；项目仍不构成生产上线、随机 A/B、线上 CTR 增益或分布式集群容量证明。
